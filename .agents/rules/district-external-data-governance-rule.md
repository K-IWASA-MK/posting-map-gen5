# District External Data Governance Rule (地区外部データ取得・保管・参照統制規則)

本規則は、汎用ポスティングマップOSの地区作成・量産・運用フローにおいて、外部公式情報源から取得する地区固有の一次原本および関連資料をどのように安全に取得・保管・参照し、Gitリポジトリと分離すべきかを定めた基本就業規則（AGENTS.md）の具現化特化ルールである。

---

## 1. 最上位原則 (Supreme Principle)

> [!IMPORTANT]
> **【最上位原則：Driveに原本 ➔ Gitに確定データ】**  
> 今後、新しい地区を作成・展開するとき、**外部から取得した地区固有の原本・一次資料は、最初から地区専用 Google Drive へ保存する**。  
> Git リポジトリには、原本そのものを作業途中の一時ファイルとして持ち込んではならない。

Git リポジトリには、以下のみを保持する：
1. **汎用ポスティングマップOS本体**（コード・アーキテクチャ・共通設計）
2. **地区の確定済み実行データ**（アプリが稼働するために確定・検証されたデータ）
3. **生成・変換・監査に必要な正式スクリプト**（`scripts/`）
4. **正式な監査証跡・意思決定記録**（`.agents/records/`）
5. **OSとして必要な標準ドキュメント・運用規程**（`docs/`, `.agents/rules/`）

---

## 2. データのライフサイクル (Data Lifecycle)

地区作成における外部データのライフサイクルは、以下の標準 8 段階フローを厳格に遵守しなければならない。

```text
  [外部公式情報源]（総務省、自治体選管、e-Stat、デジタル庁 等）
         │
         ▼
  ① 原本取得（公式公表データのダウンロード・収集）
         │
         ▼
  ② 地区専用 Google Drive へ保存（SOURCE_ARCHIVE 領域への恒久退避）
         │
         ▼
  ③ Drive 上の原本を参照（入力データとしての指定）
         │
         ▼
  ④ 生成・変換・加工（正式スクリプトによる小地域マスター/GeoJSON変換）
         │
         ▼
  ⑤ 検証・監査（人口・世帯数・境界整合性・公式公表値との全数突合）
         │
         ▼
  ⑥ 確定（機械監査ゲート通過 & 監査記録への証跡記録）
         │
         ▼
  ⑦ Git リポジトリの data/ へ配置（確定 3 点セットの配備）
         │
         ▼
  ⑧ アプリが確定データを使用（Hアプリ・Manager・Dashboard 稼働）
```

**【本質的原則】**:  
**「取得した公式原本」** と **「アプリ実行用の確定データ」** を物理的・構造的に完全分離する。

---

## 3. Google Drive に保存するもの (Drive Storage Scope)

地区作成時に外部から取得した以下の資料は、**Git リポジトリではなく、原則として地区専用 Google Drive へ保存**する。

1. **公的機関の公表資料**:
   - 総務省自治行政局選挙部等の公式資料（選挙結果調、投票率一覧 等）
   - 各自治体選挙管理委員会の公式公表資料（開票速報、投票結果、過去推移 等）
   - デジタル庁アドレス・ベース・レジストリ等の住所一次データ
2. **統計・境界データ原本**:
   - e-Stat 令和2年国勢調査小地域境界 Shapefile（原本 ZIP および展開データ）
   - 人口・世帯数等の集計表（CSV, Excel）
   - 日本郵便等の公式郵便番号マスター原本
3. **ファイル形式**:
   - PDF, XLS, XLSX, CSV, ZIP, Shapefile (shp, shx, dbf, prj)
   - 取得時点の未加工バイナリ・公的ドキュメント全般

> [!NOTE]
> 原本からアプリ用データを生成・変換した後も、将来の監査・再現性・仕様変更時の再検証に備え、元原本は Drive 上に恒久保持する。

---

## 4. Git リポジトリに保存するもの (Git Repository Scope)

Git リポジトリには、汎用OSとしての再現性とアプリケーション稼働に必要な最小限の正本資産のみを保存する。

| 分類 | 格納パス | 具体的内容 |
| :--- | :--- | :--- |
| **A. 汎用OS資産** | `active/`<br>`scripts/`<br>`.agents/rules/`<br>`docs/` | アプリケーション本体コード、保守・監査用正式スクリプト、基本就業規則、設計仕様書 |
| **B. 地区の確定実行データ** | `data/address_master.csv`<br>`data/boundaries.geojson`<br>`data/municipality_master.csv`<br>`data/area_mapping.json`<br>`data/election_history.json` | 厳格な検証と監査を通過し、アプリ（Hアプリ・Manager）が実行時に直接参照・稼働する「地区確定実行データ」（原本バイナリは含まない） |
| **C. 正式な証跡** | `.agents/records/` | 公式一次資料との突合結果、SSOT 確定記録、整合性監査レポート、意思決定記録（Markdown 表形式） |

---

## 5. scratch への原本保存の絶対禁止 (scratch Misuse Prohibition)

- **`scratch/` は外部原本の恒久的保存場所ではない**。
- 「とりあえず `scratch/` に原本をダウンロードして作業する」という運用を標準フローにしてはならない。
- 一時的なスクリプト実行や変換処理のためにローカルメモリ・一時フォルダーを利用した場合でも、**変換・監査完了後は速やかに一時中間物を削除し、Git 追跡下はもちろんローカル作業領域にも残存させてはならない**。

---

## 6. 地区固有資料と汎用OS資産の混同禁止 (Cross-District Isolation)

新地区リポジトリを作成・複製する際、前地区の一次原本（PDF, Excel, Shapefile, ZIP, 中間 GeoJSON, 一時スナップショット, 検証画像）がコピー元 Git リポジトリに残存していてはならない。
- **前地区の一次資料は新地区へ絶対に持ち込まない**（AGENTS.md 第0条・第4条厳守）。
- 新地区の外部資料は、**新地区専用の Google Drive 上に新規取得して保存**する。

---

## 7. Google Drive 保管構造 (Drive Storage Architecture)

各地区専用の Google Drive（親フォルダー `03_BRANCH/{DISTRICT_NAME}`）内に、原本専用の保管領域を設ける。

```text
03_BRANCH/{DISTRICT_NAME}/
├── {DISTRICT_NAME} (スプレッドシート)
├── {DISTRICT_NAME} 支部_STORAGE (アプリ稼働用ストレージ)
└── SOURCE_ARCHIVE/ (原本恒久保管領域)
    ├── election/ (選挙関連公式一次資料)
    │   ├── 第49回/
    │   ├── 第50回/
    │   └── 第51回/
    ├── census/ (国勢調査・e-Stat統計原本)
    └── postal/ (住所・郵便関連公的資料)
```

> [!TIP]
> フォルダー名や階層の詳細（選挙回次や統計種別）は、各地区の実態や収集資料の性質に応じて論理的に整理する。ただし、**「地区専用の原本保管領域（SOURCE_ARCHIVE）を確保し、Git から完全に隔離する」** 原則は全地区共通で不変とする。

---

## 8. 原本の追跡可能性 (Provenance & Traceability)

外部原本を Google Drive へ保存し、それを元に確定データを生成・監査した場合、以下のメタデータを監査記録（`.agents/records/record-*.md`）に明記する。

1. **情報源（発行元機関）**: （例: 岡山県選挙管理委員会、総務省、e-Stat）
2. **資料名 & 公表日**: （例: 衆議院小選挙区開票結果、2026-02-09発表）
3. **公式 URL または取得経路**: （例: `pref.okayama.jp/page/766995.html`）
4. **Drive 上の保存先 & ファイル名**: （例: `SOURCE_ARCHIVE/election/第51回/405267.xlsx`）
5. **整合性検証証跡**: ファイルサイズ、MD5 ハッシュ（必要に応じて）、および確定データ（`data/`）との突合検算結果

これにより、Git リポジトリ内に重い原本バイナリを抱え込むことなく、**「どの公式一次原本から、いかなる根拠で現在の確定データが作られたか」を第三者が 100% 検証可能な追跡可能性**を担保する。

---

## 9. 確定データの生成フロー (Deterministic Data Pipeline)

アプリケーション（Hアプリ、Manager、GAS）は、Google Drive 上の原本を直接 fetch したり動的に解釈する構造を持ってはならない。
原本から確定データへの変換は、以下の決定論的パイプラインに従う。

```text
Drive 原本 ➔ [正式スクリプト] ➔ 中間データ ➔ [機械監査ゲート] ➔ 確定 ➔ data/ 配置
```

1. **原本参照**: `scripts/` に配置された正式ツール（例: `scripts/generate-boundaries-geojson.py` 等）が Drive 原本を参照。
2. **変換加工**: 決定論的アルゴリズムにより小地域マスターや GeoJSON を生成。
3. **監査・検証**: 人口・世帯数・境界幾何のトポロジーを全数監査。
4. **Git 配置**: 検証 PASS を確認した成果物のみを `data/` へ配置し、Git コミットする。

## 10. 地区コピー時の分類マトリクス (Cloning Matrix)

汎用ポスティングマップOSをコピー元として新地区を立ち上げる際の取り扱い分類：

| 分類 | 対象ファイル・ディレクトリ | コピー時の取り扱い |
| :--- | :--- | :--- |
| **A. そのままコピー** | `active/`<br>`scripts/`<br>`.agents/rules/`<br>`docs/` (汎用マニュアル・アーキテクチャ・運用規程) | 汎用OSコアとして一切改変せず無傷でコピーする |
| **B. 新地区用に交換・生成（地区確定実行データ）** | `data/address_master.csv`<br>`data/boundaries.geojson`<br>`data/municipality_master.csv`<br>`data/election_history.json` | 新地区専用 Drive 原本から新規生成・監査した地区確定実行データへ丸ごと差し替える |
| **C. 初期化** | `data/area_mapping.json` | 新規地区では必ず空配列 `[]` に初期化する |
| **D. 持ち込み絶対禁止** | 前地区の `scratch/`<br>前地区の外部一次資料 (PDF, Excel, ZIP, Shp)<br>前地区の中間検証物・画像 | **コピー元から一切持ち込んではならない**（新地区の Drive で新規取得・管理する） |

---

## 11. 削除・保管の判定基準 (Retention & Disposal Criteria)

外部原本の取り扱いにおいて、「Git リポジトリから除外する」ことと「破棄する」ことを明確に区別する。

- **Google Drive で恒久保持するもの**:
  - 一次原本そのもの（PDF, XLS, XLSX, CSV, ZIP, Shapefile）。
  - 再現性・監査・将来の選挙区改定時に必要な公的資料。
- **完全削除（破棄）するもの**:
  - 変換過程で生成された一時ファイル、キャッシュ（`__pycache__` 等）。
  - 一時的な実行時ログ、使い捨ての単発実験スクリプト。
  - すでに確定データに集約完了し、原本から再生成可能な中間一時バイナリ。

## 12. 既存ルールとの責務分担・階層関係

本規則と既存の [district-data-transition-rule.md](./district-data-transition-rule.md) は、相互補完的な二層ガバナンスを形成する。

```text
[AGENTS.md (基本就業規則)]
      │
      ├── ① district-external-data-governance-rule.md (本規則)
      │     └─ 責務: 外部原本の取得・Drive恒久保管・追跡可能性・scratch保存禁止
      │
      └── ② district-data-transition-rule.md (次地区展開データ取り扱い規則)
            └─ 責務: Git内 data/ 確定データの同時交換・初期化・整合性判定ゲート
```

- **本規則**: 外部情報源から Google Drive への原本保管、および確定データ生成までの上流パイプラインを統制する。
- **既存規則**: 確定データ（`data/`）の Git リポジトリ内での交換、およびスプレッドシートへのプロビジョニング前の整合性判定（Rule-01 〜 Rule-04）を下流で統制する。
