## 1. エンドツーエンド情報フローと責務境界 (Information Flow)

### 1.0 外部原本から確定データへの8段階ライフサイクル (External Data Lifecycle)
「Driveに原本 ➔ Gitに確定データ」の最高位原則に基づき、公定一次資料からアプリ実行データに至るライフサイクルは以下の8段階フローを厳格に順守する。
```text
  [外部公式情報源]（総務省選管、自治体選管、e-Stat国勢調査、国交省、デジタル庁 等）
         │
         ▼
  ① 原本取得（公式公表データのダウンロード・調達）
         │
         ▼
  ② 地区専用 Google Drive へ保存（SOURCE_ARCHIVE 領域への恒久退避）
         │
         ▼
  ③ Drive 上の原本を参照（入力データとしての指定）
         │
         ▼
  ④ 生成・変換・加工（正式スクリプトによる小地域マスター/GeoJSON変換）
         │
         ▼
  ⑤ 検証・監査（人口・世帯数・境界整合性・公式公表値との全数突合）
         │
         ▼
  ⑥ 確定（機械監査ゲート通過 & 監査記録への証跡記録）
         │
         ▼
  ⑦ Git リポジトリの data/ へ配置（確定 3 点セットの配備）
         │
         ▼
  ⑧ アプリが確定データを使用（Hアプリ・Manager・Dashboard 稼働）
```
- **scratch への原本保存の絶対禁止**: `scratch/` は外部原本の恒久的保存場所ではない。一時作業で利用した場合でも、変換・監査完了後は速やかに削除し、Git追跡下やローカル作業領域に残存させてはならない。

### 1.1 アプリケーション実行時情報フロー
システム全体の実行時データの流れは、以下の単一方向フローを厳格に順守する。

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Hアプリ (現場活動アプリ)                                    │
│    ・党員が完全に自由にポスティング活動を行う (活動場所制約なし)│
│    ・現場で「誰が・いつ・どこで・何枚」を記録                   │
│    ・オフライン時は IndexedDB (syncQueue) に安全保留           │
└──────────────────────────────┬──────────────────────────────┘
                               │ データ送信 (POST JSON / liffToken / RequestId)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Backend / API (Standalone GAS)                           │
│    ・認証 (LINE LIFF ID Token による本人性検証)                │
│    ・Identity 強制解決 (クライアント送信 staffId を上書き)      │
│    ・入力値検証 (rowId, count の正当性チェック)                │
│    ・業務ルール検証・冪等性検証 (重複排除)                     │
│    ・証跡保存 (GPS座標検証、Drive 写真保存)                    │
└──────────────────────────────┬──────────────────────────────┘
                               │ 確定保存 / 排他制御 (LockService)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Database (Spreadsheet = Pure DB)                         │
│    ・発生した配布実績事実をそのまま永続化 (`配布実績YYYY-MM`)   │
│    ・スクリプト・トリガー・マクロ内包ゼロ                       │
│    ・担当エリア等の割当構造なし                                 │
└──────────────────────────────┬──────────────────────────────┘
                               │ データ集計・提供
                               ▼
             ┌─────────────────┴─────────────────┐
             ▼                                   ▼
┌──────────────────────────────┐   ┌──────────────────────────────┐
│ 4-A. Hアプリ (モチベーション) │   │ 4-B. Dashboard (全体観測)    │
│  ・自身の活動確認            │   │  ・管理者側で全体状況を把握  │
│  ・個人ランキング            │   │  ・誰が・いつ・どこで・何枚  │
│  ・「自分もやろう」という    │   │  ・地域全体の配布状況を観測  │
│    活動意欲・動機付け向上    │   │  ・活動指示・管理評価しない  │
└──────────────────────────────┘   └──────────────────────────────┘
```

### フェーズ別 責務境界マトリクス (Create → Display)

| フェーズ | 実行環境 | 主な責務 | 入力データ | 出力データ | 違反・禁止事項 |
|---|---|---|---|---|---|
| **Create** | Hアプリ (端末) | 現場での実績入力、端末GPS取得、写真撮影、UUID生成 | 党員の画面操作、端末センサー | 一時実績オブジェクト | 担当エリアの指定、活動可能地域の割当、ノルマ判定 |
| **Validate** | Backend (GAS) | LINE本人検証、Identity解決、型・値チェック、重複排除 | 受信JSON、LIFFトークン | 検証済み業務イベント | クライアント送信staffIdの盲信、支部による活動制限チェック |
| **Persist** | Backend / DB | 排他ロック下でのSpreadsheet行更新、Drive写真保存 | 検証済み業務イベント | 永続化完了レコード | スプレッドシート側での自動計算 |
| **Read** | Backend / DB | 月次シートからの実績抽出、名簿・在庫の安全な読み出し | 検索条件、セッション情報 | 生データ配列 | 機密LINE IDのクライアント返却 |
| **Aggregate** | Backend (GAS) | 全体完了率・個人ランキング・在庫サマリの動的集計 | 確定実績レコード群 | サマリ・順位オブジェクト | 評価値・ポイント新設、ノルマ未達者リスト作成 |
| **Display** | 各フロントエンド | Hアプリ: 自身の順位・枚数で動機付け / Dashboard: 全体観測 | APIレスポンスJSON | レンダリングされたDOM | ランキングの人事評価・管理利用、活動場所強制指示 |

## 2. 最重要関係モデル（担当エリア不存在の構造証明とランキングの位置付け）

Universal POSTING MAP のデータモデルにおける基本原則は、**「所属支部」と「ポスティングした場所」が完全に独立した別概念であること**である。

```text
Person (党員個人)
   ├── 組織所属 ──► Branch (所属支部: 組織上の所属先)
   │
   │ 1. performs (完全に自由なポスティング活動: 活動場所の制限・限定・選択肢化なし)
   ▼
DistributionRecord (配布実績事実)
   ├── rowId (町丁目行番号)
   ├── cityName / townName (どこで)
   ├── completedAt (いつ)
   ├── count (何枚)
   ├── staffId / staffName (誰が: Backend強制解決)
   ├── gps (latitude, longitude, accuracy: 空間証跡)
   └── photo (photoFileId, photoUrl: 物理証跡)
   │
   │ 2. aggregated into (実際の配布枚数の単純集計)
   ▼
RankingSummary (個人ランキング)
   ├── rank (順位)
   ├── staffId (表示用スタッフID)
   └── count (累計実績枚数)
   │
   │ 3. motivates (動機付け)
   ▼
配布員本人のモチベーション・活動意欲向上 ──► 「自分もやろう」と自律的に次の活動へ
```

### 【不存在の証明（絶対禁止事項）】
```text
❌ Person ────[assignedArea]─────────> Area / Region   (存在しない: 個人担当エリアの完全排除)
❌ Member ────[fixedArea]────────────> Town           (存在しない: 固定割当の完全排除)
❌ Branch ────[allowedRegion]────────> Person         (制約しない: 支部による個人の活動場所制限の完全排除)
❌ Branch ────[targetRegion]──[filter]─> PostingArea  (排除: 支部の活動対象地域を個人の可能範囲としない)
❌ Person ────[quota]────────────────> TargetCount    (存在しない: ノルマの完全排除)
```

- **ポスティングは完全に自由**:
  * 個人に担当エリアは存在しない。
  * 個人に活動可能地域を割り当てない。
  * 支部が党員個人の活動場所を制限するモデルを作らない。
  * 「支部の活動対象地域」は組織上の管轄・管理対象地域であり、「党員のポスティング可能範囲」ではない。
  * 「所属支部」と「ポスティングした場所」は別概念であり、所属支部から活動場所を制限・限定・選択肢化してはならない。
- **事実の記録**:
  * `DistributionRecord` に記録される `staffId` は、「山田さんが相生町で500枚配った」という発生した事実を記録するものであり、「相生町が山田さんの担当である」という所属・割当を示すものではない。

### 【個人ランキングの位置付けと厳格な境界】
```text
【モチベーション・サイクル（⭕ 正常な目的）】
自由なポスティング ──► 実際の配布枚数 ──► 配布実績記録 ──► ランキング集計 ──► 活動意欲向上 ──► 次の活動へ

【ランキングの管理機能化の絶対禁止（❌ 違反）】
ランキングを以下の目的に使用・設計することを厳格に禁止する：
× ノルマ設定
× 目標未達管理
× 出勤・参加管理
× 人事評価
× 配布員への指示
× 担当エリア割当
× 活動量による参加制限
× ランキング順位によるペナルティ
```
- ランキングは活動を強制するための道具ではなく、自由に活動する配布員自身のメンタル面の動機付けとして設置する。

## 3. 主要エンティティのライフサイクル

### (1) 配布実績 (`DistributionRecord`) のライフサイクル

```text
[現場入力 / 完了]
       │
       ▼
[IndexedDB保留 (syncQueue)] ◄─── (オフライン時: 永続化・指数バックオフ再送待機)
       │
       ▼ 通信確立・送信
[Backend受信・認証検証] ─── (トークン不正 / 項目異常) ──► 【REJECTED / エラー返却】
       │
       ▼ 正常検証 (LINE User ID → Staff Identity 強制上書き)
[排他書込 (LockService)] ─── (既存OK/OK重複) ──────────► 【IDEMPOTENT HIT (更新スキップ)】
       │
       ▼ 新規書込
[Database永続化 (`配布実績YYYY-MM`)]
       │
       ├─► [Dashboard リアルタイム観測表示]
       └─► [月次個人ランキング集計反映]
```

#### オフライン耐性と冪等性保証 (Offline & Idempotency)
- **RequestId (UUID v4)**: Hアプリが送信ごとに暗号学的UUID（`req_xxxx`）を生成。
- **IndexedDB キュー (`db.js`)**: 通信切断時はローカルDB（`PostingMapDB` の `syncQueue`）に保存し、FIFO順・`isProcessing` 排他・指数バックオフで再送。
- **月内1行固定および既存実績保護 (ADR-005 / ADR-009)**:
  配布実績は「1か月・1 rowId = 1行」として管理し、当月初回完了のみを記録する。同一町丁目の完了実績が既に存在する場合、別 `requestId` 操作は新規追記せず `alreadyCompleted: true` として返し既存実績を保護する（同月再配布なし、翌月に新しい月次シートで未配布から新しく開始する）。システム全体の監査・操作証跡（活動履歴シート・エラーログシート等）は追記専用（Append-Only）の不変ログとして保持する。
- **Timestamp Winner (上書きルール) の採用禁止 (REJECT)**:
  タイムスタンプ比較によって既存の完了実績行を無秩序に上書き・更新することは厳禁。
- **Q列・D列による冪等性・進捗保護照合 (Durable SSOT Authority / ADR-009)**:
  同一 `requestId` の再送時は、スプレッドシート Q列（`requestId`）と照合し、新規書き込みをスキップして既存レコード情報を返却する（HTTP 200, duplicate: true）。また、当月完了済みの町丁目（D列 `completedAt` 存在）に対する別 `requestId` 操作は上書きせず `alreadyCompleted: true` として返し、既存実績を保護する。
- **配布完了確定の厳格な条件 (ADR-011 / ADR-012 / ADR-013)**:
  写真撮影・GPS取得の完了はあくまで下書き確認（READY_TO_SUBMIT / DRAFT）であり、この時点で `p.isDone = true` を確定させてはならない。真の配布完了（COMPLETED）は、**Backend永続化および受諾成功（Spreadsheet [配布実績YYYY-MM] への書き込み完了 / getRowStatus === null かつ accepted !== false）** のみを確定条件とする。非受諾終端（accepted: false / STALE_MONTH）時はキューから削除されるが未完了を維持する。

### (2) 配布員 Identity (`StaffIdentity`) のライフサイクル

```text
[LINEログイン] ──► [LIFF ID Token 取得]
                        │
                        ▼
           [Backend: getStaffIdentity]
           (LINE User ID で名簿原本を検索)
           ┌────────────┴────────────┐
       登録あり                     登録なし
           │                         │
           ▼                         ▼
   [STAFF IDENTITY CONFIRMED]    [UNREGISTERED]
   ・Staff ID 解決                ・表示名入力
   ・Hアプリ即時利用開始          ・registerStaff (POST)
                                  ・名簿原本へ A〜D列追記
                                  ・Staff ID 発番
                                     │
                                     ▼
                                 [ACTIVE STAFF]
```

- **Active**: 認証済みLINE User ID と紐づき、配布実績・チラシ在庫の登録が許可された状態。
- **Inactive / Withdrawn**: 本人の申し出または管理者による名簿からの無効化。以後のAPIリクエストは `NOT_REGISTERED` として遮断。

## 4. 月次データ保存アーキテクチャの比較と決定

現行システムに存在する「原本系 ＋ 当月YYYY-MM系」の設計妥当性を、Universal POSTING MAP の要件に照らして多面的に検証する。

### 方式比較分析

| 評価軸 | 方式1: 原本＋月次シート分割方式 (現行) | 方式2: 単一履歴テーブル方式 (全件追記) | 方式3: ハイブリッド方式 (最新月+年次アーカイブ) |
|---|---|---|---|
| **概要** | 毎月1日に原本シートから当月用シート（`配布実績2026-09` 等）を自動複製し、月ごとに独立シートで運用。 | 1つの巨大なシートに `yearMonth` 列を持たせて全月の実績を連続追記する。 | 当月シートのみアクティブとし、過去月は年度別シートや外部DBに自動退避する。 |
| **読込性能 (GAS)** | **◎ 高速**: 当月分（桑名市の場合337行）のみを読み込むため、GASのメモリ・実行時間制限（6分）に余裕。 | **✕ 劣化大**: 1年で数千〜数万行、全国展開で数十万行に達し、GASの `getValues()` がタイムアウト。 | **◯ 良好**: 当月分のみを参照するため高速。 |
| **書込・排他制御** | **◎ 局所化**: 当月シートのみをロック更新するため、過去データ破損リスクが皆無。 | **△ 競合大**: 全月の操作が1シートに集中し、行ロック競合が発生しやすい。 | **◯ 局所化**: 当月シートのみを更新。 |
| **容量制限耐性** | **◯ 良好**: 月ごとにシートが分かれるため、1シートあたりのセル数上限に達しにくい。 | **✕ 危険**: Google Spreadsheet の上限（1000万セル）および描画制限に急速に接近。 | **◎ 最優秀**: 過去データを別シートや外部へ逃がせるため長期運用に最適。 |
| **過去監査・履歴保全** | **◎ 容易**: シートタブ（`2026-08`, `2026-09`）を選択するだけで過去の配布事実をそのまま確認可能。 | **△ フィルタ必須**: 閲覧時にスプレッドシート上で複雑なフィルタ操作が必要。 | **◯ 良好**: 年次シート等で確認可能。 |
| **月替わり運用負荷** | **△ トリガー必要**: 毎月1日に原本から月次シートを自動生成するバッチが必要。 | **◎ 不要**: 単に新しい年月で追記するのみ。 | **△ バッチ必要**: 月次移行バッチが必要。 |

### Universal POSTING MAP の採用決定

> **【採用案】: 方式1（原本＋月次シート分割方式）を Universal 標準として継承・固定する。**

#### 採用理由・論理的根拠
1. **GAS および Spreadsheet (Pure DB) の制約との適合性**:
   - Google Apps Script の実行時間（最大6分）およびメモリ制限下において、300〜1,000行程度の町丁目マスターを月単位で独立保持する方式1は、最もレスポンスが速く、API遅延（LCP/タイムアウト）を最小化できる。
2. **過去月データの安全な凍結（不変性の保証）**:
   - 月が替わると前月のシート（例: `配布実績2026-08`）への書き込みが停止し、自然に「確定アーカイブ」として凍結される。誤って過去の実績を上書き・破壊する事故がアーキテクチャ上防止される。
3. **実績のある `MonthlySheetResolver` の活用**:
   - 現行コードの `MonthlySheetResolver` は、当月シート名の解決SSOTとしてシンプルかつ堅牢に稼働しており、追加の複雑なDBエンジンや外部移行を必要としない。

## 5. HアプリとDashboardの表示・公開境界（未確定事項の明示）

### (1) 確定している表示境界

#### 1. Hアプリ (現場活動アプリ — モチベーション・動機付け中心)
- **自身の配布員情報**: Staff ID、登録表示名
- **地図ピン**: 配布済み / 未配布 / 作業中の色分け（自由な活動の支援）
- **自身の個人ランキング**: 現在の順位、当月累計配布枚数（「自分もやろう」という活動意欲の喚起）
- **全体ランキング**: 上位者の匿名化Staff IDと枚数（他者の活動によるポジティブな刺激）
- **チラシ在庫一覧**: 保管場所自治体と保管者名、自身の在庫残数
※ Hアプリのランキングは配布員本人のモチベーション向上のために表示され、管理・監督のための情報は一切含まない。

#### 2. Dashboard (統括観測アプリ — 全体状況の把握・観測中心)
- **全体の進捗率**: 完了町丁目数 / 総町丁目数、累計配布枚数
- **配布実績一覧**: 誰が・いつ・どこで・何枚配ったか（発生した事実の記録）
- **現場写真およびGPS測位情報の監査プレビュー**: 物理的・空間的証跡の確認
- **全配布員の名簿および実績合計**: 支部全体の活動概況の把握
- **スタッフ別実績一覧（現行ランキング表示）**: 既存実装（`manager.js: renderMainStageRecords`）に存在する実績順一覧は、「誰がどれくらい活動したか」という**地域全体の配布状況を管理者が観測・把握するためのもの**である。Hアプリのモチベーション目的をDashboardの管理・評価・ノルマ思想へ置き換えてはならない。DashboardからHアプリへ活動場所を指示したり、ノルマ未達を管理・指導する機能は設けない。

### (2) 🔵 未確定事項（勝手に仕様化を禁止する項目）
以下の項目は、現場のプライバシー保護、通信コスト、または運用合意が未確定であるため、Gate 2 では**「非公開 / 未実装」を維持**し、後続フェーズの検討事項とする。

1. **他党員の個別配布実績のHアプリ公開**:
   - 「誰が、いつ、どこで配ったか」の全配布員詳細履歴をHアプリ内で一般公開する仕様は現在確定していない。プライバシーや自由な活動の阻害リスクを考慮し、Gate 2 では公開仕様を追加しない。
2. **掲示板（Bulletin）の保持期間・削除ポリシーの運用値**:
   - 投稿の物理的保持期間（例: 30日、90日）および不適切投稿の通報・非表示ルール。
3. **チラシ受渡要請におけるLINE Messaging API Push通知の費用・クォータ制限**:
   - LINE Push通知の月間送信数上限と代替手段（アプリ内通知・手動連絡）の運用実態。
4. **境界GeoJSONのモバイル向け頂点削減（Simplify）率**:
   - 1.0MBのGeoJSONを低スペック端末向けに軽量化する際の具体的許容誤差。
5. **過去選挙実績データのUI連携**:
   - `election_history.json` の活動画面での表示要否。

## 6. 新地区スプレッドシート（DB）の正規ライフサイクル (District Database Lifecycle)

親Standalone GAS 1本化（Universal Engine）において、新地区の独立したスプレッドシート（DB）を安全に立ち上げ、運用へ投入するための正規ライフサイクル（9段階プロトコル）を規定する。

```text
① テンプレート原本複製
       ↓
② 03_BRANCH フォルダへ配置
       ↓
③ SYSTEM_INFO 初期化
       ↓
④ 地区データ投入 (町丁目マスター原本等)
       ↓
⑤ DISTRICT_REGISTRY 登録 (親GAS Script Properties)
       ↓
⑥ 接続確認 (親GASからの openById 疎通)
       ↓
⑦ API 疎通確認 (Web App エンドポイント経由の getSystemSummary 応答)
       ↓
⑧ LINE / LIFF 側 districtId 設定確認 (data/config.js との突合)
       ↓
⑨ 実機確認 (Hアプリ・Dashboard での画面・活動確認)
       ↓
【正式稼働 Operational DB】
```

### (1) 正規9段階プロトコルの詳細

| 段階 | 工程名 | 実行主体 | 実施内容 | 完了条件 |
| :--- | :--- | :--- | :--- | :--- |
| **①** | テンプレート複製 | 管理者 / サービスアカウント | 公式原本 `POSTING_MAP_EMPTY_TEMPLATE` を複製する。※既存地区本番DBの複製は永久禁止。 | コピー完了スプレッドシートの生成 |
| **②** | 03_BRANCH配置 | 管理者 / サービスアカウント | Google Drive の公式保管場所 `03_BRANCH` フォルダ配下にスプレッドシートを格納・命名（例: `OKAYAMA-01`）。 | 指定フォルダへの安全な配置 |
| **③** | SYSTEM_INFO初期化 | 管理者 / スクリプト | 第1シート `SYSTEM_INFO` に地区名、契約終了日、管理パスワード等の初期値を書き込む。 | 地区名がスプレッドシート名と完全一致 |
| **④** | 地区データ投入 | 管理者 / ツール | 当該地区の `address_master.csv` を基に原本シートへ町丁目行データを投入する。 | 原本行数とCSV町丁目数が完全一致 |
| **⑤** | REGISTRY登録 | 管理者 (Script Properties) | 親GASの `DISTRICT_REGISTRY` に `districtId: spreadsheetId` のエントリを追加する。 | JSONパース可能かつキー・値が正常永続化 |
| **⑥** | 接続確認 | 管理者 / 診断スクリプト | 親GAS環境から `SpreadsheetApp.openById(ssId)` で対象スプレッドシートが開けることを確認。 | 例外なしでスプレッドシートオブジェクト取得 |
| **⑦** | API疎通確認 | 管理者 / curl / テスト | Web App URL に対して `{ action: "getSystemSummary", districtId: "..." }` を投げ、200 OK を確認。 | 正常な JSON サマリ応答 |
| **⑧** | クライアント設定確認 | 管理者 / フロントエンド | 当該地区の `data/config.js` の `districtId` が登録名と 1 文字の狂いもなく一致することを確認。 | 設定値の完全一致 |
| **⑨** | 実機確認 | 管理者 / 検品者 | ブラウザ / LINE 実機で Hアプリ・Dashboard を開き、ピン表示および動作を確認。 | 検品チェックリスト全項目 PASS |

### (2) 二段階SSOT境界（DISTRICT_REGISTRY と SYSTEM_INFO）

地区DBの管理において、二重管理を防ぎつつ確実な整合性を保つため、以下の二段階検証境界を厳格に順守する。

```text
【第1段階: 接続解決SSOT】
  親GAS Script Properties: DISTRICT_REGISTRY
      ├─ 役割: 「どのSpreadsheetか（接続先ID）」の唯一のSSOT
      └─ 解決: districtId ➔ Spreadsheet ID
           │
           ▼ (openById)
【第2段階: 実体状態SSOT】
  対象Spreadsheet: SYSTEM_INFO シート
      ├─ 役割: 「そのSpreadsheetは何地区で、利用可能か」の唯一のSSOT
      ├─ 照合: SYSTEM_INFO 内の地区名 === リクエストの districtId (取り違え防止)
      └─ 判定: 契約終了日 >= 現在日 (契約有効性判定)
           │
           ▼
      [二重検証完了 ➔ 業務処理実行]
```
