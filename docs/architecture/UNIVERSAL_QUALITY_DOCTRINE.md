# Universal 品質ドクトリン (Universal Quality & Reliability Doctrine)
## Universal POSTING MAP Supreme Quality Doctrine — Gate 1 Canonical Specification

> 本書は、最高位設計契約（`docs/architecture/01_DESIGN_CONTRACT.md`）に基づき、
> 先行開発および現場運用で得られた事故・障害・課題の知見を昇格・統合し、
> 全地区共通（Universal POSTING MAP）における再発防止・品質保証原則を規定した **Canonical Architecture 正本規格** である。
>
> 全ての AI 社員（`architect`, `execution`, `worker`, `auditor`, `deployer`）および開発者は、
> 以下の 12大ドクトリンを永久不変の設計原則として遵守しなければならない。

---

## 最上位原則：権限境界と自己判断の絶対禁止

> **AIが問題を発見したことと、AIに修正権限があることは別である。**
>
> 発見した不整合・負債・バグを、MASTERの事前許可なく「改善」「リファクタリング」と称して修正することは永久に禁止される。
> 予期せぬ状態を発見した場合は即座に作業を停止（HARD STOP）し、MASTERへ報告して指示を仰ぐこと。

---

## Universal 12大品質ドクトリン

---

### 第1条：Identity直列化の禁止と Optimistic First Paint
- **教訓事象**: Hアプリ起動時に、認証基盤（LIFF）初期化からバックエンド Identity 検証 API 完了までを直列同期（ウォーターフォール）で待機したため、通信不安定な現場で白画面フリーズが発生した。
- **根本原因**: 画面初期描画（First Paint）がネットワーク越しのサーバー応答にブロックされる同期的・直列的ライフサイクル。
- **普遍規格ルール**:
  1. **Optimistic First Paint（先行描画）**: クライアントキャッシュに既存認証情報が存在する場合は、Identity API の完了を待たずにメインUIを即時先行表示する。
  2. **バックグラウンド並行検証**: Identity 検証はバックグラウンド Promise として並行実行し、不整合検知時のみ安全に画面ロックまたは再認証へ誘導する。
- **検証規格**: 起動完了時間およびローカルキャッシュ先行表示の自動テスト。

---

### 第2条：可視性・サイズ確定前の地図初期化禁止
- **教訓事象**: Google Maps の初期化が、DOM要素が非表示（`display: none` / `hidden`）の状態で実行され、コンテナサイズ `0px × 0px` と認識されて地図がグレーアウトした。
- **根本原因**: SPAにおけるDOM表示タイミングと非同期スクリプト読み込み完了コールバックの競合（Race Condition）。
- **普遍規格ルール**:
  1. 地図コンテナ要素が可視化され、非ゼロ（Width > 0, Height > 0）の物理サイズを持つことが確認されるまで、Map インスタンス化を実行してはならない。
  2. 画面切り替え時に既存インスタンスが存在する場合は、再生成せず `resize` イベントを発火して再適合させる。
- **検証規格**: 実ブラウザエミュレーションによる地図コンテナの実描画サイズ（非ゼロ）検証。

---

### 第3条：地図 Loader の単一窓口性（SSOT）の厳守
- **教訓事象**: 複数モジュールや画面遷移時に別々に地図 API の `<script>` タグを動的挿入したため、多重読み込み警告とコールバック多重発火、メモリリークが発生した。
- **根本原因**: 外部スクリプトのローディング責任が分散し、グローバルなロード状態管理（SSOT）が欠如していたこと。
- **普遍規格ルール**:
  1. 地図 API のローディングは、Hアプリ内の指定モジュール（`app.js: loadGoogleMapsApi`）を唯一の実行窓口（SSOT）とする。
  2. グローバルロード完了フラグによる厳格な多重抑止ガードを常時維持する。
  3. 管理者画面（Manager Dashboard）では Leaflet 等の別系統を採用し、Google Maps Loader との競合を物理的に遮断する。
- **検証規格**: DOM 内の地図 API `<script>` タグが最大1件のみ存在することの機械検査。

---

### 第4条：現場活動UIと管理者観測UIの完全物理分離
- **教訓事象**: 配布員が片手で操作するモバイルUIに、管理者向けの全体集計・監視・名簿管理機能が混入し、現場の認知的負荷と操作性を著しく損なった。
- **根本原因**: 「現場活動」と「全体観測」という本質的に異なる2つの関心事を単一アプリに混同したこと。
- **普遍規格ルール**:
  1. **完全物理分離**: 配布員用Hアプリ（`active/h-app/`）は現場活動（自律的な場所選択・配布記録・チラシ登録・個人実績確認）のみを担当する。
  2. **全体観測の集約**: 全体進捗・集計・名簿管理・在庫把握は Manager Dashboard（`active/manager/`）に集約し、Hアプリ側には一切持ち込まない。
  3. ノルマ、強制割当、他者監視機能の実装を永久に禁止する。
- **検証規格**: アーキテクチャ非干渉・機能境界監査の自動実行。

---

### 第5条：オフライン耐性と IndexedDB 先行永続化
- **教訓事象**: 電波の弱い住宅地や地下道等でデータ送信を行った際、通信切断によって入力した配布枚数や写真データが消失した。
- **根本原因**: すべてのデータ登録がネットワーク通信成功を前提とした直接 API 送信で実装されていたこと。
- **普遍規格ルール**:
  1. 配布登録等の更新操作は、まずクライアントローカルの IndexedDB（`syncQueue`）に永続保存する。
  2. 通信復旧時にバックグラウンドで自動再送（指数バックオフ）を行う。
  3. 各リクエストには暗号学的 UUID による `requestId`（冪等性キー）を付与し、二重登録をサーバー側で排除する。
- **検証規格**: IndexedDB オフラインキューおよび再送調停のユニットテスト。

---

### 第6条：モック成功と実機動作の峻別（実機エビデンス主義）
- **教訓事象**: PCブラウザ環境でテストが全て成功していたが、スマートフォン実機の WebView 環境でセーフエリア崩れ、タッチ無反応、GPSタイムアウトが発生した。
- **根本原因**: デスクトップ環境とモバイル実機 WebView における制約差（CSS `env()`, タッチイベント, メモリ上限）をモックで吸収できていなかったこと。
- **普遍規格ルール**:
  1. モックテストの成功はリリース可否の十分条件ではない。
  2. 実機画面サイズ、LINE WebView 特有の制約、タッチ挙動を含む実機エミュレーションテストを必須ゲートとする。
  3. 完了の定義（DoD）には客観的なランタイム動作エビデンスを義務付ける。
- **検証規格**: モバイル実機解像度・タッチイベントを網羅したブラウザ自動テスト。

---

### 第7条：コード同期（push）とバージョン配備（deploy）の厳格峻別
- **教訓事象**: `clasp push` によるスクリプト同期を行っただけで配備完了と誤認し、Web App のデプロイ更新を怠ったため、本番環境で旧バージョンが稼働し続けた。
- **根本原因**: 開発時スクリプト保存（HEAD）と本番公開デプロイ（Versioned Deployment）の二重構造の混同。
- **普遍規格ルール**:
  1. `clasp push` は単なるファイル同期であり、デプロイではない。
  2. 本番環境への反映は、記録された Deployment ID への明示的なバージョン更新手続きのみをもって成立する。
  3. デプロイ後は必ずエンドポイント疎通確認を行い、最新バージョンが返却されることを客観確認する。
- **検証規格**: デプロイバージョン整合性の機械検証。

---

### 第8条：スプレッドシート Pure DB 原則と Standalone GAS
- **教訓事象**: スプレッドシート側にコンテナバウンドスクリプトが残存し、意図しないトリガー発火でシート構造が破損、Standalone GAS API と競合した。
- **根本原因**: コンテナバウンド型から Standalone 型への移行時における旧スクリプト・トリガーの切り離し漏れ。
- **普遍規格ルール**:
  1. **Spreadsheet = Pure DB**: スプレッドシート内には一切のスクリプト、カスタム関数、トリガーを配置しない（コード完全ゼロ）。
  2. **GAS = Standalone only**: 全てのバックエンド処理は独立した単独 Standalone GAS プロジェクトとして管理する。
  3. コンテナバウンドスクリプトの作成・復元・依存・編集を永久に禁止する。
- **検証規格**: スプレッドシートのバウンドスクリプト非存在確認。

---

### 第9条：モバイル端末負荷を考慮したポリゴン遅延描画
- **教訓事象**: 数百〜数千の町丁目境界ポリゴン（1MB超）を地図上に一括全数描画したため、端末がメモリ不足でクラッシュ・操作不能になった。
- **根本原因**: モバイル端末の GPU・メモリ制約を考慮しない一括大量レンダリング。
- **普遍規格ルール**:
  1. 地図初期表示は大枠のみとし、ズームレベルと表示領域に応じて必要な町丁目ポリゴンのみを遅延描画する。
  2. 事前ビルドにおいてトポロジーを保ったポリゴン簡略化（Simplify）を適用する。
  3. 画面外の非表示ポリゴンは適切にメモリからアンロードする。
- **検証規格**: モバイル環境における描画時間およびメモリ消費量の測定。

---

### 第10条：AI 開発のための関心事分離（Separation of Concerns）
- **教訓事象**: 2,000〜3,000行超の長大ファイルに多種多様な処理が混在していたため、AI がコンテキストを誤認し意図しないデグレを発生させた。
- **根本原因**: モジュール分割の不足、単一責任の原則の崩壊。
- **普遍規格ルール**:
  1. ファイルサイズを適切な粒度（目安300〜500行以内）にモジュール分割する。
  2. UI描画（Stateless）、状態管理（State）、通信（API）、データモデル（Model）を明確に分離する。
  3. AI が局所的なコンテキストだけで安全に変更・テストできる疎結合構造を維持する。
- **検証規格**: ファイル行数リミット監視およびアーキテクチャ境界静的解析。

---

### 第11条：AI による未依頼変更の絶対禁止（No Silent Changes）
- **教訓事象**: AI が「改善」「リファクタリング」と称して指示範囲外の関数やコードを無断で書き換え、既存の動作保証を破壊した。
- **根本原因**: AI の行動境界に対する規律・就業規則の欠如。
- **普遍規格ルール**:
  1. **No Plan → No Proceed → No Implementation**: 計画立案と MASTER 明示承認なしの実装・変更は絶対禁止。
  2. **No Silent Changes**: 変更前に「対象ファイル、関数・行、変更内容、変更理由、変更しない範囲」を日本語で事前宣言する。
  3. **Scope Lock & 最小侵襲**: 指定範囲外のコード不可侵。最小限の行数のみ変更。「ついで」の改善は絶対禁止。
  4. **差分照合必須**: 実装後、必ず `git diff` で事前宣言と実際の変更内容を照合し、宣言外変更が1行でもあれば即時失敗（HARD STOP）とする。
- **検証規格**: `scripts/check-scope.mjs` によるスコープ外変更の機械遮断。

---

### 第12条：1-in-1-out 原則と Zombie Code の即時完全撤去
- **教訓事象**: 新機能追加時に旧コードや旧設定を「念のため」と残した結果、新旧ロジックが併存して保守者が混乱、古いコードが誤用された。
- **根本原因**: 移行完了時における旧資産の完全撤去（Decommissioning）プロセスの欠如。
- **普遍規格ルール**:
  1. 新ロジックへの移行・検証が完了した旧コード・旧設定は、即座に安全に完全撤去する。
  2. 「念のためコメントアウト」「使われない関数の放置」「旧ファイルの残存」を永久に禁止する。
  3. 現物台帳（`03_CURRENT_H_APP_INVENTORY.md`）において、全ファイルの生存状態（現役 / 廃止）を厳格に追跡する。
- **検証規格**: 未使用コード・旧ファイル残存のゼロ検査（K1 Gate）。
