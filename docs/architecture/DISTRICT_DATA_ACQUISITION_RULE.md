## 1. 目的と最上位絶対原則（Supreme Principles）

本規程は、Universal POSTING MAP における新地区展開（プロビジョニング）およびマスターデータ（`address_master.csv`, `boundaries.geojson`, `municipality_master.csv`）の生成において、**「人間によるデータ取得作業の完全排除（ゼロ手作業）」** と **「第1段階 Area Skeleton（3列骨格）確定と第2段階 属性・境界付与の厳格分離」** を担保するための標準実行規範である。

### 【原則 1】ゼロ人間介入の原則（Zero Human Intervention）— ABSOLUTE
- 地区マスターの生成に必要な公定一次資料の調達は、**100% AIエージェントが自律スクリプトにより実行**しなければならない。
- ユーザー（人間）にブラウザでダウンロードさせたり、フォルダーへの配置を指示・依頼することは**永久に禁止**する。
- 対象地区（構成自治体コード5桁）を確定するだけで、すべての調達・解凍・検証が完全自動で完結しなければならない。

### 【原則 2】Phase 1 Area Skeleton と Phase 2 後段属性付与の厳格分離原則 — ABSOLUTE
地区データの生成は、以下の2段階（Phase 1 / Phase 2）に厳格に分離し、後段データが第1段階の骨格（行集合・町名・順序・`rowId`）を支配・汚染してはならない。

1. **第 1 段階（Phase 1: Area Skeleton 確定 — 3列骨格生成）**:
   - 最初に、対象選挙に適用される法令の施行版から公式区割りを確定する（§4.1）。
   - 次に、構成市町村ごとに **国土交通省 位置参照情報「大字・町丁目レベル」の最新版** を住所の母集合として取得し、区割りを当てはめて対象町域を確定する（§3.1, §4.1）。
   - 母集合に正規化・名称衝突検査・整列・採番を行い `city_name` / `town_name` / `rowId` を確定する（§4.2〜§4.5）。
   - **丁目の包含**: 公式に「丁目」が存在する場合は、丁目まで `town_name` に含める。
   - **下位分割・人工名称の禁止**: `town_name` より下位の小字・方角・通称・地番範囲・人工的括弧名称は、全国共通の公式ソースから一意取得できない限り、**探索・推測・生成・地区固有辞書補完を行わない**。
   - **Phase 1 成果物スキーマ（3列のみ）**:
     ```csv
     rowId,city_name,town_name
     ```
   - **`rowId` の採番**: 最終的な `city_name` / `town_name` の順序確定後に `1..N`（1始まりの連続整数、欠番・重複なし）を採番する。
   - **後段データの混入禁止**: Phase 1 の Skeleton 決定に e-Stat、`households`、`population`、`latitude`、`longitude`、`boundaries`、投票率等を一切使用してはならない。

2. **第 2 段階（Phase 2: 後段属性・境界付与 — Attribute & Boundary Enrichment）**:
   - Phase 1 で確定した3列 Area Skeleton（`rowId,city_name,town_name`）を不変の基準（Authority）として受け取る。
   - 最新の国勢調査小地域境界データを動的解決（§4.6）し、代表座標（`latitude`, `longitude`）、世帯数（`households`）、人口（`population`）、小地域コード（`e_stat_code`）、および境界ポリゴン（`boundaries.geojson`）を後段責務として付与し、最終 8列マスターCSV（`data/address_master.csv`）および `provenance.json` を完成させる。

### 【原則 3】公式町字粒度原則（Official Town Granularity Doctrine）— ABSOLUTE
- `docs/architecture/ADDRESS_EXTRACTION_RULE.md` に基づき、`town_name` は公式に存在する町字名（公式に丁目が存在する場合は丁目まで含めた名称）で確定する。
- e-Stat 側の調査区分割（枝番）に合わせて人工的な方角名（`（北部）`、`（北東部）` 等）や小字括弧名（`（〇〇）`）を合成・推測・地区固有辞書補完することを禁止する。

### 【原則 4】原本はDrive・確定データはGit（Drive Storage & Provenance Doctrine）— ABSOLUTE
- **「Driveに原本 ➔ Gitに確定データ」**: 外部から取得した地区固有の原本・公定一次資料は、最初から地区専用 Google Drive（`SOURCE_ARCHIVE` 領域）へ恒久保存する。
- Git リポジトリには、汎用OS本体、検証・監査済みの確定実行データ（`data/`）、正式スクリプト、監査記録のみを保持し、原本バイナリをGitに持ち込まない。

### 【原則 5】既存稼働地区データの非遡及保護原則（Non-Migration Principle）— ABSOLUTE
- 既に確定・稼働している既存地区の `data/**`（`address_master.csv`, `boundaries.geojson`, `municipality_master.csv`）および既存の `rowId` は、本規程の改定によって遡及的に再生成・改番・Migrationしてはならない。

## 2. 8列マスターCSV作成 13工程パイプライン（13-Step Production Pipeline）

8列マスターCSV（`address_master.csv`）および追跡Provenanceの自律調達・生成は、以下の **13工程（Step 1 〜 Step 13）** の厳格なシーケンスに従って執行される：

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 【Phase 1: Area Skeleton 確定 — 3列骨格生成】                            │
│  Step 1: 自治体コードを入力（city_code群）                             │
│  Step 2: 国土交通省 位置参照情報「大字・町丁目レベル」データ取得       │
│  Step 3: デジタル庁 アドレス・ベース・レジストリ（ABR）照合            │
│  Step 4: 案A衝突回避正規化・ABR五十音順整列 ➔ 3列Skeleton生成           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼ 3列 Area Skeleton (rowId,city_name,town_name)
┌───────────────────────────────────┴────────────────────────────────────┐
│ 【Phase 2: 後段統計・空間属性付与 — 8列マスターCSV確定】                │
│  Step 5: 最新国勢調査年度を動的確認（最新完全共通年度の自律採用）       │
│  Step 6: e-Stat小地域境界データ（DBF/SHP）取得                          │
│  Step 7: 空間結合カーディナリティ監査（1:1 / 1:N / 1:0 / N:1 判定）     │
│  Step 8: 必要時だけ外部Reconciliation（1:0 空小地域 8属性Evidence検証） │
│  Step 9: 座標・人口・世帯数・e_stat_code付与（PIP内部点決定論的導出）   │
│  Step 10: Polygon / MultiPolygon / hole 多重包含トポロジー検証         │
│  Step 11: 8列マスターCSV生成（rowId,city_name,town_name,lat,lon,hh,pop,estat）│
│  Step 12: 構造化Provenance生成（全42件空小地域の完全8属性Evidence保持） │
│  Step 13: sort-address-master.py による再整列・全件監査（diff -u == 0）│
└────────────────────────────────────────────────────────────────────────┘
```

## 3. 調達データソース仕様と段階別責務

### 3.1 Phase 1（Area Skeleton 確定用）：データソースと役割
| 役割 | データソース | 使用範囲 |
| :--- | :--- | :--- |
| **住所の母集合（正本）** | 国土交通省 位置参照情報「大字・町丁目レベル」の**最新版**（市区町村コード単位で自動取得） | `city_name` / `town_name` はこの母集合からのみ作る。使用列は「市区町村名」「大字町丁目名」 |
| **公式区割り** | 対象選挙に適用される法令の施行版（衆院小選挙区は公職選挙法 別表第一）。市町村内の区域記述を町丁目へ照合する場合は、当該市町村が公表する公式の町名・区域対応資料 | 対象町域の選別のみ（§4.1） |
| **読み仮名（補助情報）** | デジタル庁 アドレス・ベース・レジストリ（ABR）町字マスター | 整列専用（§4.4）。町域の追加・削除・改名には使用しない |

- **版の扱い**: 「最新版を使う」ことが規則であり、特定の版番号を恒久値として固定しない。メタデータの年・年度表記（「令和〇年」「令和〇年度」等）および提供元明示の原資料作成日・取得日は Provenance に記録する（§7.2）。
- **非抽出項目（Phase 1 で使用禁止）**: 小字・通称名、街区符号・地番、代表緯度・経度、人口、世帯数、e-Stat境界。

### 3.2 Phase 2（後段属性・境界付与用）：総務省統計局 e-Stat 国勢調査小地域データ等
- **提供元**: 政府統計の総合窓口（e-Stat）等
- **責務**: Phase 1 で確定した Area Skeleton の各行に対する地理・統計属性（`latitude`, `longitude`, `households`, `population`, `e_stat_code`）および境界ポリゴン（`boundaries.geojson`）の後段付与。
- **注意**: Phase 2 のデータソースの都合によって Phase 1 の `rowId,city_name,town_name` を分割・統合・改名・再採番してはならない。

## 4. Phase 1 Area Skeleton 確定・採番ルール

### ルール 4.1: 公式区割りの確定と適用（Electoral Boundary Application）
1. **適用法令の施行版の特定**: 対象選挙（選挙種別と、選挙期日または公示・告示日）を特定し、その時点で適用される法令の版を e-Gov 等の公式法令データで確認する。確認対象は次の3点とする。
   - 当該時点で施行されている版
   - 当該時点までに施行される未施行改正
   - 改正法附則の経過措置（適用開始となる選挙の範囲など）
2. **区割りの確定**: 上記で特定した版の区域規定から、対象選挙区を構成する市町村と、市町村の一部のみが属する場合の区域記述を確定する。
3. **区割りの適用**: 構成市町村ごとに母集合（§3.1）を取得し、次のとおり対象町域を選別する。
   - 市町村の全域が属する場合：その市町村の母集合の全町域を対象とする。
   - 市町村の一部のみが属する場合：法令の区域記述（例：`〇〇市△△地区管内`）を、当該市町村が公表する公式の町名・区域対応資料で **町丁目単位** に照合して選別する。照合資料は外部原本として扱い、スクリプト内に地区専用の対応辞書を持たない。
4. **HARD STOP 条件**（推測による補完を禁止する）:
   - 適用される法令の版、または経過措置の適用関係が一意に決まらない場合
   - 市町村内の区域を町丁目へ照合できる公式資料が存在しない場合
   - 1つの町丁目が複数の選挙区にまたがる、または属する選挙区を一意に判定できない場合

### ルール 4.2: 正規化と名称衝突回避（Normalization & Collision Avoidance: Plan A）
- **`city_name`**: 母集合の「市区町村名」から **郡名のみを除去** する（原資料は郡部で郡名を含む）。
  - 例: `〇〇郡△△町` ➔ **`△△町`**
  - 政令指定都市の区は **市名＋区名を保持** する。例: `〇〇市△△区` ➔ **`〇〇市△△区`**（区名は除去しない）
- **`town_name`（原則と衝突回避: 案A）**:
  - 原則として母集合の「大字町丁目名」から、先頭の形式的な「大字」接頭辞（`^大字`、ただし町名自体が「大字」のみの場合を除く）を除去する。それ以外の表記（`ケ` / `ヶ` 等の字体を含む）は変更しない。
  - **大字除去衝突時の原文保持（案A汎用ルール）**: 同一自治体内において、先頭「大字」の除去によって別の独立した公式町域（異なる大字町丁目コードを持つ町域）と正規化名称が重複（衝突）する場合、**衝突するレコードの原文名称（「大字〇〇」表記）をそのまま保持して独立した町域として分離維持**する。
  - **特定町名のハードコード禁止**: スクリプトや規程内に実在の特定自治体・町名を条件分岐として記述することは永久に禁止する。衝突判定は全レコードのコードと原文名称に基づく汎用アルゴリズムとして自律判定する。
- **丁目の扱い**: 公式データに丁目が存在しない町字は町字名そのものを1行とし、丁目が存在する町字は各丁目まで含めた名称をそれぞれ1行とする。
  - 例: `大字〇〇` ➔ **`〇〇`**（非衝突時）／ `△△町` ➔ **`△△町`** ／ `□□町一丁目`, `□□町二丁目`

### ルール 4.3: 下位階層の生成禁止と名称衝突の停止条件（No Sub-Town Fabrication & Strict Collision Stop）
- `town_name` より下位の小字・方角（`北部`/`南部`/`北東部`等）・通称・地番範囲・人工的括弧名称（`〇〇（△△）` 等）は、全国共通の公式ソースから一意取得できない限り、**探索・推測・生成・地区固有辞書補完を一切行わない**。
- **区別不能時の HARD STOP**: ルール 4.2 の案A（原文名称保持）を適用してもなお同一自治体内で同一町名に異なる大字町丁目コードが存在する場合、または正規化後の異表記同士が衝突して区別できない場合は、自動統合・推測改名を禁止し直ちに **FATAL HARD STOP** する。
- 規程・Skill・テスト・ログにおける禁止例や説明に実在地区名・町名を使用することを避け、架空名称（「架空市」「サンプル町」「大字サンプル町」等）を使用する。

### ルール 4.4: 整列・ABR階層仕様・外部根拠データ（Deterministic Ordering & Reconciliations）
1. **読み仮名の取得元と階層仕様**: デジタル庁 アドレス・ベース・レジストリ（ABR）町字マスター。
   - 市町村: `city_kana`（区名を含む `city_name` では `city_kana + ward_kana`）
   - 町字階層仕様（`machiaza_type` に基づく同一階層からの名称・読み取得）：
     - `machiaza_type = 1` (大字): `oaza_cho` と `oaza_cho_kana`
     - `machiaza_type = 2` (丁目): 基底町名 `oaza_cho`（読み: `oaza_cho_kana`）と `chome`（丁番: `chome_number` 数値）
     - `machiaza_type = 3` (小字): `oaza_cho` が存在する場合は `oaza_cho + koaza`（読み: `oaza_cho_kana + koaza_kana`）、`oaza_cho` が空の場合は `koaza`（読み: `koaza_kana`）
2. **整列規則**:
   - 市町村: 公式読み仮名の五十音順。
   - 町域: 同一 `city_name` 内では町域の公式読み仮名の五十音順とし、同じ基底町名の丁目は**丁目の数値順（1, 2, 3...）**とする（丁目の読み文字列を単純連結して比較しない）。
   - 案Aにより原文保持された町域（例: `大字〇〇`）は、ABR照合時に無条件で「大字」を除去せず、原文名称および正規化名称の対応を維持して正確に基底読みを取得する。
3. **原本検証と読み解決の責務分離**:
   - ABR原本の検証（`verify_abr_master`）では、原本自体の物理構造・コード体系・種別整合性のみを検証し、原本行における読み仮名の非空を一律に要求しない（原本自体の読み欠損による不当停止を排除）。
   - 母集合町域に対する読み仮名の完全性は、後述の外部根拠データ補完後の生成段階（QG-2(d)）で判定する。
4. **読み乖離の推測補完禁止と外部根拠データ（JSON固定）**:
   - 国交省母集合とABRの間で異体字・冠称差・新旧町名差等の乖離が存在する場合、コード体系の同一視や座標近接による自動推測同定を永久に禁止する。
   - 当該自治体が公表する公式の変更資料・対応資料で同一性を客観確認し、**外部根拠データ（JSON形式固定: `<city_code>:<town_code>` 複合キー）** に記録して入力として与える。
   - 外部根拠JSONのスキーマ:
     ```json
     {
       "<city_code>:<town_code>": {
         "raw_town_name": "母集合原文町名",
         "reconciled_reading": "公式読み仮名",
         "reconciled_target_official_name": "対応先公式原本名称",
         "source_provider": "発行元機関名",
         "source_document_title": "公的資料名",
         "source_url": "公定URL",
         "source_section_or_page": "該当箇所/頁",
         "verified_date": "YYYY-MM-DD"
       }
     }
     ```
   - 同一性が確認されても原本側で読みが欠落している場合、自治体公表資料等の公的読み資料から補完し、その根拠を上記JSONに明記する。公的資料による同一性・読みの確認が得られない町域は「未解決」として HARD STOP し、MASTER へ報告する。
   - 外部根拠データは読み解決と同一性確認にのみ使用し、住所母集合の追加・削除・改名には一切使用しない。
   - 特定地区専用の読み辞書をスクリプト内にハードコードしてはならない。

### ルール 4.5: `rowId`（`1..N`）の確定採番（Deterministic Numbering）
- 新規地区の Phase 1 Area Skeleton 生成では、ルール 4.4 で全 `(city_name, town_name)` の最終順序を確定した後に、先頭から **`rowId` を `1..N`（1始まりの連続整数）で一意に採番**する。
- 一方、**既存稼働地区の確定済みデータ** については、既存の `rowId`（`1..N`）を100%保護し、遡及的な改番・振り直し（Migration）を絶対に行わない。

### ルール 4.6: 空間結合カーディナリティ監査と 1:0 空小地域8属性Evidence完全保存
1. **空間結合カーディナリティ（0:1 / 1:1 / 1:N / N:1 / 1:0）の厳格判定**:
   - `1:1`: 骨格町域と e-Stat 小地域が 1 対 1 で一意一致。統計・座標属性を直接付与。
   - `1:N`: 1つの骨格町域が複数の e-Stat 小地域に分割されている場合、各小地域レコードを行として展開し、それぞれの決定論的内部点（PIP）を導出。
   - `N:1`: 複数の骨格町域が同一の `e_stat_code` を主張した場合は即時 **FATAL HARD STOP**（二重計上防止）。
   - `0:1`: 対象選挙区外の自治体・小地域レコードは厳格に除外（混入防止）。
   - `1:0`: 骨格町域に対応する e-Stat 小地域が存在しない場合、原則 **FATAL HARD STOP**。
2. **1:0 空小地域の例外成立条件（8属性Evidence Gate）**:
   - 当該町域に独立した小地域集計境界が存在しない公的事由が客観確認され、外部Reconciliationファイル（`--estat-reconciliation`）にキー `"<city_code>:<skeleton_town_name>"` で以下の **8必須項目すべてが非空文字列** で登録されている場合のみ、統計列を空欄（`households=""`, `population=""`, `e_stat_code=""`）とし、Phase 1 骨格のMLIT基準点座標を保持して通過を認める：
     1. `city_code`: 5桁自治体コード
     2. `skeleton_town_name`: 骨格町域名
     3. `reconciled_status`: `"no_independent_estat_small_area"`
     4. `source_provider`: 発行元・公定調査元機関名
     5. `source_document_title`: 公定資料名
     6. `source_url`: 公定URL
     7. `source_section_or_page`: 当該事由・該当箇所
     8. `verified_date`: 確認年月日（YYYY-MM-DD）
3. **最終 Provenance への 8属性Evidence 完全永続化（Full Evidence Persistence）**:
   - 一時的な外部Reconciliationファイルを破棄・削除した後も、完成地区の `provenance.json` 単体で空欄理由・公的根拠が恒久追跡できるよう、対象レコードの `estat_reconciliation_evidence` オブジェクトに上記8項目すべてを完全保存する。

### ルール 4.7: 多重入れ子トポロジー幾何契約（Ring Containment Hierarchy & Even-Odd Rule）
1. **多重包含トポロジー（Nested Topology）の普遍的解法**:
   - 全国小地域境界における「外周（depth 0）➔ 穴/湖（depth 1）➔ 穴の中の島（depth 2）➔ 島の中の池（depth 3）...」という入れ子構造を幾何学的に正しく処理するため、単一外周＋穴の制約を廃止し、**リング包含深度階層（Ring Containment Hierarchy）** を採用する。
2. **深度偶奇と回転方向（CW/CCW）の厳格整合性**:
   - 偶数深度（depth 0, 2, 4...）: **Solid 実領域（外周・島）** ➔ CW（符号付き面積 < 0）
   - 奇数深度（depth 1, 3, 5...）: **Void 空間（穴・湖）** ➔ CCW（符号付き面積 > 0）
   - 深度偶奇と符号付き面積の回転方向が矛盾するリングはトポロジー不整合として即時 **FATAL HARD STOP**。
3. **Even-Odd 包含判定と代表点導出**:
   - 点 $P(x, y)$ を包含する境界リング総数 $K$ が奇数（$K \pmod 2 == 1$）の場合のみ実領域内部（INSIDE）と判定し、偶数の場合は穴・外部（OUTSIDE）として厳格排除する。
   - 代表座標導出（Point-in-Polygon）において、単純頂点平均を絶対禁止し、上記 Even-Odd 判定を満たす決定論的内部点（point-on-surface 相当）のみを採用する。

## 6. 禁止事項（Prohibited Actions）— ABSOLUTE

1. **手作業ダウンロードの要請**: ユーザー（人間）にデータ取得・ZIP解凍を指示すること。
2. **Phase 1 への後段データ混入**: Phase 1 Area Skeleton（`rowId,city_name,town_name`）の決定に、e-Stat、`households`、`population`、`latitude`、`longitude`、`boundaries`、投票率等を使用すること。
3. **下位小字・方角・人工括弧名称の生成・辞書補完**: `town_name` より下位の小字・方角・通称・人工的括弧名称を探索・推測・生成したり、特定地区専用の辞書・オーバーライド表をコード内に持つこと。

5. **外部有料API依存**: Google Maps Geocoding API等の外部課金APIや検索結果をデータ生成パイプラインの前提にすること（完全オフライン・公定オープンデータで完結させること）。

7. **前地区一次原本の持ち込み絶対禁止**: 前地区の一次原本（PDF, Excel, Shapefile, ZIP, 中間GeoJSON等）を新地区Gitリポジトリへ持ち込んではならない。新地区の外部原本は新地区専用Driveで新規取得・管理する。

## 7. 原本恒久保管・追跡可能性統制 (Drive Storage & Provenance)

### 7.1 Google Drive 保管構造 (Drive Storage Architecture)
各地区専用の Google Drive（親フォルダー `03_BRANCH/{DISTRICT_NAME}`）内に、原本専用の保管領域を設ける。
```text
03_BRANCH/{DISTRICT_NAME}/
├── {DISTRICT_NAME} (スプレッドシート Pure DB)
├── {DISTRICT_NAME} 支部_STORAGE (アプリ稼働用ストレージ)
└── SOURCE_ARCHIVE/ (原本恒久保管領域)
    ├── election/ (選挙関連公式一次資料: 第49回/, 第50回/, 第51回/)
    ├── census/ (国勢調査・e-Stat統計原本)
    └── postal/ (住所・郵便関連公的資料)
```

### 7.2 原本の追跡可能性と骨格対応根拠 (Provenance & Skeleton Evidence)
外部原本を Google Drive へ保存し、確定データを生成・監査した場合、以下のメタデータを監査記録（`.agents/records/`）に明記する。
1. **情報源（発行元機関）**: （例: 都道府県選挙管理委員会、総務省、e-Stat、デジタル庁）
2. **資料名 & 公表日**: （例: 衆議院小選挙区開票結果、公表年月日）
3. **公式 URL または取得経路**: 公定公開URL
4. **Drive 上の保存先 & ファイル名**: （例: `SOURCE_ARCHIVE/election/...`）
5. **整合性検証証跡**: ファイルサイズ、SHA-256 / MD5 ハッシュ、確定データ（`data/`）との突合検算結果
6. **版・年度・日付（住所の母集合および読み仮名）**: 取得日、年度・年表記、版、原資料の作成日（原資料同梱のメタデータ等で確認した値）
7. **区割り根拠**: 法令名・法令番号、参照した版の改正法令と施行日、確認した未施行改正、経過措置の有無と適用判断、市町村内照合に用いた公式資料（発行元・公表日・URL）、取得日
8. **件数の位置付け**: 記録する件数は検証時点の参考値であり、後続の生成作業の固定目標として扱わない
9. **住所骨格の原本対応根拠データ**: 3列 CSV（`rowId,city_name,town_name`）とは別の根拠データ（`skeleton_provenance.json` 等）に、各町域の `rowId`、自治体コード（`city_code`）、国交省町丁目コード（`town_code`）、原文名称（`raw_town_name`）、正規化名称（`clean_town_name`）、原本代表緯度・経度、および出典情報を保存する。再整列（`sort-address-master.py`）等でもこの根拠データを入力として受け取り、外部根拠 JSON の複合キーを解決して同一の名称・順序を再現する。

### 7.3 決定論的データ生成パイプライン (Deterministic Data Pipeline)
アプリケーション（Hアプリ、Manager、GAS）は、Google Drive 上の原本を直接 fetch したり動的に解釈する構造を持ってはならない。
```text
Drive 原本 ➔ [Phase 1: Area Skeleton (3列) + 根拠データ] ➔ [Phase 2: 後段属性・境界付与] ➔ [機械監査ゲート] ➔ 確定 ➔ data/ 配置
```
1. **Phase 1（Area Skeleton 生成）**: 住所の母集合（§3.1）に区割り適用・正規化・案A名称衝突回避・整列（§4）を行い、`rowId,city_name,town_name`（3列のみ）を決定論的に確定・`1..N` 採番し、同時に原本対応根拠データを記録。
2. **Phase 2（後段属性・境界付与）**: 確定した Area Skeleton に対し、後段で統計・座標・GeoJSON境界を付与。
3. **監査・検証**: Master Triad 閉包整合性およびトポロジーを全数機械監査。
4. **Git 配置**: 検証 PASS を確認した成果物のみを `data/` へ配置し、Git コミットする。
