# ADR-004: クライアントオフラインキュー・排他制御・同時実行制御 (Client Offline Queue, Locking, and Concurrency Control)

- **Status**: ADAPTED (ADAPT)
- **Date**: 2026-09-22
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `docs/architecture/01_DESIGN_CONTRACT.md` §2, `docs/api/API_CONTRACT.md` §3, §10, §11, §13, §14

---

## 1. Context (背景と課題)

現場でのポスティング活動では、電波の届きにくい路地や集合住宅の屋内・地下など、不安定なネットワーク環境での利用が前提となる。そのため、オフライン下でも活動実績を損失なく記録し、電波回復時に安全にサーバーへ同期する仕組みが不可欠である。
一方で、バックエンドである Google Apps Script (GAS) および Google Spreadsheet は、リレーショナルデータベースのようなきめ細かなトランザクション機構を持たない。複数の端末から同時に実績送信が行われた場合、スプレッドシートの最終行取得や行追加においてレースコンディション（競合書き込み）が発生し、データが破損または上書き消失するリスクがある。

また、外部提案において「GASロック保持時間を1秒未満とする」「GAS同時実行数を30とする」等の固定値が示されたが、これらはスプレッドシートや Google Drive API の実測 I/O 速度を無視した非現実的な制約であり、無条件な採用は重大なシステム障害を引き起こす。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、現行契約に基づき以下のクライアントキュー方式およびバックエンド排他制御モデルを採用する。

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Client Offline Queue (Hアプリ / PWA)                     │
│    ・IndexedDB (`PostingMapDB` / `syncQueue`)                │
│    ・順序保証: FIFO (先入れ先出し)                          │
│    ・多重送信防止: `isProcessing` フラグによる排他制御      │
│    ・リトライ: Exponential Backoff (1s, 2s, 4s, 8s, 16s; 最大3回) │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS POST (`completeDistribution`)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Backend 排他制御 (Standalone GAS API)                    │
│    ・`LockService.getScriptLock()` によるクリティカルセクション保護 │
│    ・タイムアウト設定: `waitLock(15000)` (15秒)             │
│    ・ロック保持時間: 必要最小限とするが「1秒未満」は不採用   │
│    ・ロック獲得失敗時: HTTP 429 または 503 を即座に返却     │
└──────────────────────────────┬──────────────────────────────┘
                               │ 排他制御下での安全なアペンド
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Database (Google Spreadsheet DB)                         │
│    ・`appendRow` または末尾判定＋一括書き込み               │
└─────────────────────────────────────────────────────────────┘
```

### 【詳細規程と制約事項】
1. **クライアント側オフライン整合性 (Hアプリ)**:
   - 完了操作はまずローカルの IndexedDB (`PostingMapDB` の `syncQueue` ストア) に `PENDING` 状態で保存される。
   - 送信処理中は `isProcessing` フラグを立てて二重起動を防止し、必ず FIFO（登録日時順）で直列送信する。
   - ネットワーク障害や一時的サーバーエラー時は、指数バックオフアルゴリズム（初期待機1秒、最大16秒、上限3回）に従って再試行する。
2. **バックエンド側排他制御 (GAS ScriptLock)**:
   - バックエンドの書き込み処理は `LockService.getScriptLock()` によってプロセス間排他制御を実施する。
   - ロック待機時間は `waitLock(15000)`（15秒）とする。
   - **「ロック保持時間1秒未満」の不採用（REJECT）**:
     Spreadsheet への行挿入、PinStatus の更新、および Google Drive への画像バイナリ保存処理には、Google 内部の通信遅延を含め数秒を要することが通常である。「1秒未満」を強制した契約は成立不可能であり、タイムアウト例外を多発させるため採用しない。
3. **同時実行数と高負荷時挙動の扱い**:
   - Google Apps Script の同時実行制限について、根拠のない固定値（例: 30）を契約として固定しない。
   - 高負荷時（同時リクエスト集中時）の具体的なスループット、キュー溢れ率、ロック競合耐性については現時点では **「GAP（要実測・負荷テスト）」** として扱い、Gate 5 以降の実機検証で実態を確定する。

## 3. Consequences (影響と効果)

### ポジティブな影響
- 電波断線時でも端末ローカルに配布実績が確実に保全され、電波回復時に自動送信される。
- クライアントの `isProcessing` およびバックエンドの `ScriptLock` により、通信の瞬断や連打に伴う二重書き込みやスプレッドシートの競合破損が防止される。
- 無理な「1秒未満」制約を排除することで、Google Drive や Spreadsheet I/O の現実的な実行時間を許容し、正常完了率を担保する。

### ネガティブな影響 / リスクと緩和策
- **ロック待機によるレイテンシ**: ロック待ちが最大15秒発生する可能性があるが、クライアント側が非同期かつバックグラウンドでキュー処理を行うため、ユーザーの画面操作はブロックされない。
- **高負荷時の同時実行制限**: GAS の同時実行クォータを超過した場合に 429/503 が返却されるため、クライアント側の指数バックオフが適切にリトライを吸収するよう実装を検証・維持する。
