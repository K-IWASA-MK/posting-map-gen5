# ADR-006: 認証・Identity解決・シークレット境界 (Authentication, Identity Resolution, and Secret Boundary)

- **Status**: ADAPTED (ADAPT - HMAC主認証案はREJECT、LINE LIFF主認証＋ScriptPropertiesシークレット境界を採用)
- **Date**: 2026-09-22
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `AGENTS.md` §2, `docs/architecture/01_DESIGN_CONTRACT.md` §2, §3, `docs/data/DATA_DICTIONARY.md` §2, `docs/api/API_CONTRACT.md` §2, §6, §7

---

## 1. Context (背景と課題)

外部のアーキテクチャ提案において、フロントエンド（Hアプリ）とバックエンド（GAS API）間の主認証として「HMAC-SHA256 共有鍵署名（リクエストヘッダーにタイムスタンプとハッシュ値を付与）」を導入する案が提示された。

しかし、この方式には以下の致命的なセキュリティ上の欠陥と不整合が存在する：
1. **フロントエンドへの秘密鍵漏洩の不可避性**: Hアプリはブラウザおよび PWA 環境（HTML/JavaScript）で動作するクライアントアプリケーションである。クライアントに共有鍵（HMAC Secret）を保持させた場合、ブラウザの開発者ツールや逆コンパイルにより即座に鍵が抽出・漏洩する。
2. **LINE LIFF 認証モデルとの完全な矛盾**: POSTING MAP では既に現場活動員の本人確認・連絡手段として LINE LIFF を主認証基盤として採用している。無効な HMAC 署名体系を追加することは、複雑性を増大させるだけでなく、認証の根本的な安全性を損なう。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、外部提案の HMAC 主認証案を正式に**却下（REJECT）**し、既存の設計契約に基づき **LINE LIFF Bearer Token + サーバー側強制解決 + ScriptProperties シークレット隔離** を正式な認証・Identity・シークレット境界として確定する。

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Hアプリ (Client)                                         │
│    ・LINE LIFF ログイン ──► LIFF ID Token (Bearer Token)    │
│    ・ヘッダー: `Authorization: Bearer <liff_id_token>`      │
│    ・フロントエンドにはいかなるシークレットも保持しない     │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS (Bearer Token)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Standalone GAS Backend (`v2_api.js`)                     │
│    ・CacheService.getScriptCache() 照会 (TTL: 30分 / 1800s) │
│    ・キャッシュミス時: LINE Profile API でトークン直接検証  │
│    ・lineUserId を抽出し、Staff Master と照合               │
│                                                             │
│    【Identity 強制解決チェーン (Untrusted Client Input)】    │
│    lineUserId ──► staffId, staffName, branchId を強制特定   │
│    (クライアント送信の staffId / branchId は完全破棄)        │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Secret Isolation Boundary (シークレット隔離境界)          │
│    ・PropertiesService.getScriptProperties()                │
│    ・Spreadsheet ID, Drive Folder ID, LINE 設定値等の保管   │
│    ・リポジトリおよびフロントエンドへの秘密情報露出ゼロ     │
└─────────────────────────────────────────────────────────────┘
```

### 【詳細規程と制約事項】
1. **Hアプリ主認証 (LINE LIFF Bearer Token)**:
   - Hアプリのすべての更新系・個人関連APIリクエストは、LINE LIFF Bearer Token（`Authorization: Bearer <token>`）を必須とする。
   - バックエンド（GAS）は LINE 公式の Profile API (`https://api.line.me/v2/profile`) を用いてトークンの署名と有効期限を直接検証する。
   - 外部通信の負荷軽減とレスポンス向上のため、検証済みの `lineUserId` は GAS の `CacheService` に 30分間（1800秒）キャッシュする。
2. **Identity 強制解決チェーン (Client Untrusted 原則)**:
   - クライアントから送信された `staffId`, `staffName`, `branchId` は、認証・認可・実績記録の証拠として一切信用しない（Client-supplied values are UNTRUSTED）。
   - バックエンドが検証済み `lineUserId` を基に Staff Master シートを照会し、身元（Identity）をサーバー側で強制的に決定・上書きする。
3. **HMAC 主認証案の完全却下 (REJECT)**:
   - Hアプリと GAS 間の主認証として HMAC 方式は採用しない。
   - 「フロントエンドに秘密情報を絶対に配置しない（No Secrets in Frontend）」原則を厳格に順守する。
4. **ScriptProperties によるシークレット隔離境界**:
   - スプレッドシートID、Google Drive フォルダID、外部接続トークン等の機密情報は、すべて Google Apps Script の `ScriptProperties` に隔離して保存する。
   - ソースコード、設定ファイル（`config.js` 等）、リポジトリ内のいかなる文書にも秘密情報を平文で記述してはならない。

---

## 3. Consequences (影響と効果)

### ポジティブな影響
- クライアント側に共有シークレットが存在しないため、ブラウザ側からの鍵漏洩リスクが原理的に排除される。
- LINE LIFF の公式 OAuth/OIDC 仕組みに準拠することで、現場活動員の本人確認が安全かつ確実に実行される。
- クライアント側でのパラメータ改ざん（他人名義での実績送信）がサーバー側の強制解決によって完全に防止される。

### ネガティブな影響 / リスクと緩和策
- **LINE API 障害時の影響**: LINE Profile API の障害時に認証が影響を受ける可能性があるが、`CacheService` による 30分間のキャッシュにより、一時的なネットワーク瞬断や API 遅延への耐性を確保する。
- **未登録ユーザーの扱い**: LINE ログインに成功しても Staff Master に `lineUserId` が存在しない場合は、適切なエラー（HTTP 403 / USER_NOT_REGISTERED）を返却し、不正な利用を遮断する。
