# ADR-007: レガシー互換性・実行環境制約と将来近代化境界 (Legacy Compatibility, Execution Environment Constraints, and Future Modernization Boundary)

- **Status**: ADAPTED (ADOPT - 当面の設計制約として採用。ただし永久固定ではなく将来の近代化境界を明記)
- **Date**: 2026-09-22
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `AGENTS.md` §1, §4, `docs/architecture/01_DESIGN_CONTRACT.md` §2, `docs/api/API_CONTRACT.md` §2

---

## 1. Context (背景と課題)

現行の POSTING MAP クライアント（Hアプリ・Dashboard）およびバックエンド（Google Apps Script）は、運用実績を持つ既存コードベースであり、以下の実装構造および実行環境上の制約を有している：
1. **フロントエンドの実装形態**: 即時実行関数式（IIFE: Immediately Invoked Function Expression）によるスコープ保護と、グローバルオブジェクト（`window`）に単一インスタンスを公開・保持するシングルトン（Singleton）パターンが多用されている。
2. **Google Apps Script (GAS) の実行環境特性**: GAS は単一のグローバル実行コンテキストにすべての `.gs` / `.js` ファイルが展開されるため、モダンな ES Modules (`import` / `export`) を直接解釈できない。

外部のアーキテクチャ提案において、「IIFE およびシングルトンを Universal POSTING MAP の恒久的・永久的実装原則として確定する」という案が提示された。しかし、現状のコード構造を「永久原則」として固定化することは、Gate 8 以降におけるモダンなモジュールシステム（ESM、TypeScript、ビルドパイプライン導入等）への技術的近代化の道を塞ぐことになり、将来の拡張性と保守性を著しく損なう。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、**「現状の互換性維持」と「将来の技術的近代化」を明確に分離**し、以下の 3 区分に基づいて決定・管理する。
**「現状維持＝永久固定」という解釈は明確に禁止する。**

```text
┌─────────────────────────────────────────────────────────────┐
│ A. 現行コード・GAS実行環境の依存構造                        │
│    ・フロントエンド: IIFE およびグローバル Singleton パターン│
│    ・GAS: グローバル名前空間での関数・定数共有              │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ B. Gate 8 までの当面の設計制約 (互換性維持フェーズ)         │
│    ・Gate 0〜7 の移行期間中は現行構造との完全互換性を最優先  │
│    ・無計画なモジュール化や大規模リファクタリングを禁止     │
│    ・最小侵襲の原則に従い、既存の IIFE / Singleton 構造を尊重│
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ C. 将来の実装方式と近代化境界 (Gate 8 以降の再構築フェーズ) │
│    ・IIFE / Singleton は「永久原則」ではない                │
│    ・Gate 8 以降でモジュール化 (ESM), TypeScript, Vite 導入 │
│      等が必要となった場合は、別途新たな ADR を起草する       │
│    ・MASTER の明示的承認を経て計画的にアーキテクチャを刷新  │
└─────────────────────────────────────────────────────────────┘
```

### 【明確に分離された 3 つの階層】
1. **A. 現行コード・GAS実行環境に存在する依存構造**:
   - 既存のフロントエンド資産および GAS は、IIFE によるスコープ分離とシングルトン参照に依存して稼働している事実を認識・記録する。
2. **B. Gate 8 以降の再構築時に互換性を壊さないための当面の設計制約**:
   - Universal POSTING MAP の基盤整備（Gate 0〜7）においては、現行コードの安定稼働とゼロ・リグレッションを最優先とする。
   - したがって、当面の間は既存の IIFE / シングルトン構造を尊重し、動作を破壊するような急進的変更を行わないことを設計制約とする。
3. **C. 将来の実装方式と近代化境界 (Future Modernization Boundary)**:
   - IIFE やシングルトンを「システムの永久的な実装原則」とは位置づけない。
   - Gate 8 以降において、フロントエンドのビルドツール導入（Vite / Rollup）、型安全化（TypeScript）、ES Modules 化、依存性注入（DI）など、保守性・テスト容易性を高める近代化が必要となった場合は、**別途個別の ADR を起草し、MASTER の承認を得てから判断・移行する**。

---

## 3. Consequences (影響と効果)

### ポジティブな影響
- **短期的な安定性**: 既存の稼働中システムに対する不要なモジュール化の押し付けを防止し、確実な後方互換性と最小侵襲の移行を実現する。
- **中長期的な近代化の確保**: アーキテクチャを永久固定しないことで、技術の進歩やシステムの成長に合わせた将来のコード近代化への扉が維持される。

### ネガティブな影響 / リスクと緩和策
- **技術的負債の共存**: 当面の間は IIFE / シングルトンという古い JavaScript パターンを維持・管理する必要があるが、これは Gate 8 以降の計画的近代化までの過渡的措置として位置づけ、境界をコントロールする。
