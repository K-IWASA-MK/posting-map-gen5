# ADR-003: Universal エンジンと地域差データ吸収 (Universal Engine and Data-Driven Regionalization)

- **Status**: ADAPTED (ADAPT)
- **Date**: 2026-09-22
- **Deciders**: Universal POSTING MAP Architecture Board
- **Consulted**: `AGENTS.md` §1, §3, `docs/architecture/01_DESIGN_CONTRACT.md` §1, §3, `docs/data/DATA_DICTIONARY.md` §0, `docs/data/DATA_LIFECYCLE.md` §1, `docs/api/API_CONTRACT.md` §1

---

## 1. Context (背景と課題)

過去のポスティングマップ開発および運用において、新地区（自治体・支部）を展開するたびに共通Runtimeコード一式を個別コピーし、自治体名やロジックを直接書き換えて個別分岐を作成する複製改変モデルが採られていた。
この結果、以下の致命的な問題が発生した：
1. **コードの断片化と技術的負債の増殖**: 各地区ごとにバグ修正や機能改善がバラバラに適用され、システム全体の振る舞いが乖離した。
2. **セキュリティ脆弱性・保守不能**: 共通の不具合や脆弱性が発見されても全地区への水平展開が不可能となった。
3. **極端な固定化への懸念**: 一方で外部レビュー等において「共通エンジン（`active/`）は一切変更してはならない」という極端な解釈が示されたが、これでは共通の不具合修正や将来的な機能拡張・近代化（Gate 8以降の改善）までもが永久に凍結されてしまう。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、**「1地区 = 1完成アプリ = 1単独フォルダー = 1単独リポジトリ = 1単独ドメイン」**（AGENTS.md §1）のアーキテクチャ原則を正式採用し、共通Runtime（`active/`）を Universal Engine として全地区共通化して以下の設計原則を確定する。

```text
┌─────────────────────────────────────────────────────────────┐
│                 Universal Engine (`active/`)                │
│   ・全地区共通のコアロジック (Hアプリ, Dashboard, Backend GAS)│
│   ・地域固有のハードコード (地区名, 自治体コード, URL等) はゼロ  │
└──────────────────────────────┬──────────────────────────────┘
                                │ データ注入 (Data-Driven)
                                ▼
┌─────────────────────────────────────────────────────────────┐
│                   Master Data (`data/`)                     │
│   ・`address_master.csv`      (地理マスター: 町丁目・世帯数) │
│   ・`boundaries.geojson`      (ポリゴン境界データ)          │
│   ・`municipality_master.csv` (自治体定義)                  │
│   ・`config.js`               (初期座標・ズーム・自治体設定) │
└─────────────────────────────────────────────────────────────┘
```

### 【基本原則と境界条件】
1. **Universal Engine の統一（共通Runtimeコード改変禁止）**:
   - すべての地区リポジトリは同一の Universal Engine（`active/`）を共通Runtimeとして配備する。
   - 共通Runtime（`active/`）をコピーして地区固有の個別分岐や独自修正を加える行為は恒久的に禁止する（ABSOLUTE）。地区差は `data/` で吸収する。
2. **地域差のデータ吸収 (Data-Driven Regionalization)**:
   - 地域差（市区町村界、町丁目リスト、世帯数、地図初期表示位置、レイヤー構成等）はすべて `data/` 配下の静的マスターデータおよび設定ファイルによって吸収する。
3. **`active/` の変更境界と進化プロトコル**:
   - `active/` に対する「地域特化のための変更」は厳格に禁止する。
   - 一方で、全地区に資するバグ修正、共通セキュリティパッチ、共通UI改善、将来的なアーキテクチャ刷新については、MASTERの明示的承認および厳格な Gate 統制（8-Stage Protocol）を経ることで `active/` の変更を認める（「永久凍結」とはしない）。
4. **リポジトリ境界の絶対遵守 (Repository Boundary)**:
   - 作業対象リポジトリの Git root を絶対境界とし、SSD上に存在する他地区リポジトリや過去フォルダーを「参考」「比較」を含め一切参照しない（AGENTS.md §3）。

## 3. Consequences (影響と効果)

### ポジティブな影響
- 全国どの自治体・支部であっても、`data/` のマスターデータを差し替えるだけで展開可能となり、展開コストと保守負荷が最小化される。
- バグ修正や新機能が共通Universal Engine（`active/**`）の標準仕様として一元管理され、各地区リポジトリへ同一コードとして水平展開することで、全地区へ均質に反映可能となる。
- 地区固有の例外処理がコードベースに混入するリスクが完全に排除される。

### ネガティブな影響 / リスクと緩和策
- **地域固有の特殊要件の吸収**: 特定地区のみの特殊な行政区分や要望が生じた場合、コードを安易に分岐させず、データスキーマの汎用化またはプラグイン設計（Gate 8以降検討）によって吸収する必要がある。
- **データ不整合の影響**: `data/` のマスターデータ不備が直接エンジンに影響を与えるため、Gate -1 による構文・スキーマ監査を厳格に義務付ける。
