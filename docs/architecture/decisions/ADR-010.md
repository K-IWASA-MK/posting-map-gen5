# ADR-010: 親Standalone GAS 1本化・単一Deployment Version更新方式・動的地区ルーティング (Parent GAS Single-Project Versioned Deployment & Dynamic District Routing)

- **Status**: ACCEPTED
- **Date**: 2026-09-23
- **Deciders**: Universal POSTING MAP Architecture Board / MASTER
- **Consulted**: `AGENTS.md`, `docs/architecture/01_DESIGN_CONTRACT.md`, `ADR-009.md`, `docs/architecture/CURRENT_ARCHITECTURE.md`

---

## 1. Context (背景と課題)

Universal POSTING MAP は、[AGENTS.md](../../../AGENTS.md) 第1条において「1地区 = 1完成アプリ = 1単独フォルダー = 1単独リポジトリ = 1単独ドメイン」を定めている。
クライアント層は地区ごとに独立インスタンスとして配備されるが、バックエンド層においては地区ごとにGASプロジェクトを複製することを永久に禁止し、以下の不変構造を厳守する：
```text
[各地区独立Client (1地区=1repo=1domain)] ─── 単一親Standalone GAS ─── 単一固定Web App URL ─── 動的DBルーティング
```

しかし、これまでの実証検討において「新地区ごとに `clasp create` で GAS プロジェクトを新規作成し、Web App をデプロイする」という旧方式（マルチプロジェクト運用）の発想が残存していた。

この旧方式には以下の重大なアーキテクチャ上の欠陥が存在した：
1. **GASプロジェクトの無制限増殖**: 地区が増えるたびに GAS プロジェクトが複製され、コード重複排除原則に違反する。
2. **Web App URL（APIエンドポイント）の分裂**: 地区ごとに接続先 URL が異なり、クライアント側の設定保守が複雑化する。
3. **初回OAuth承認の人的負荷**: 地区ごとに人間がブラウザで「アクセスを承認」する 1 クリック作業が発生し、自動プロビジョニングを阻害する。
4. **一括更新・ロールバックの困難性**: エンジン更新時に全地区の GAS へ個別プッシュ・デプロイする必要があり、分散デプロイ障害のリスクを抱える。

---

## 2. Decision (決定内容)

Universal POSTING MAP では、**親 Standalone GAS 1本化・単一 Deployment Version 更新方式・動的地区ルーティング** を正式採用する。

```text
                 ┌─────────────────────────┐
                 │ Universal Repository    │
                 │ active/ = 共通Runtime    │
                 │ data/   = 地区データ     │
                 └────────────┬────────────┘
                              │ clasp push
                              ▼
                 ┌─────────────────────────┐
                 │ 親Standalone GAS 1本     │
                 │ Universal Engine Core   │
                 └────────────┬────────────┘
                              │
                    単一固定 Web App URL
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
       KUWANA DB        OKAYAMA-01 DB     MIE-04 DB
       Spreadsheet      Spreadsheet       Spreadsheet
```

### 【詳細決定事項】

#### 1. 単一親Standalone GASプロジェクトの維持
- Universal Engine 用の Standalone GAS プロジェクトは、全地区共通で **「たった1つ」** のみ作成・維持する。
- 地区追加・展開時に `clasp create` や GAS プロジェクトの複製を行うことを永久に禁止する。

#### 2. 単一Deployment IDの固定とVersion更新
- Apps Script の Versioned Deployment 機構を活用する。
  - **Version**: 変更不能なコードスナップショット（Version 1, Version 2, ...）。
  - **Deployment**: 特定の Version を外部公開するエンドポイント。
- Universal Engine の正式 Deployment ID を **単一の本番 Web App として固定** し、コード更新時は「同一 Deployment ID を新しい Version へ更新（redeploy）」する。
- **ロールバック**: 障害発生時は、同一 Deployment ID の向け先を即座に旧 Version へ再指定する（URL は一切不変）。
- **3大識別子の独立管理**:
  1. `Script ID`: 親GASプロジェクト自体の不変識別子
  2. `Deployment ID`: 本番公開エンドポイントの固定識別子
  3. `Web App URL`: クライアントがアクセスする固定URL (`https://script.google.com/macros/s/<DEPLOYMENT_ID>/exec`)
- **Web App 実行主体**:
  - `Execute as: Me`（デプロイ者権限）: 全クライアントからのアクセスを親GASの統一権限で実行し、各地区スプレッドシートへのアクセス権限を一元化する。
  - `Who has access: Anyone`（全員アクセス可能）: LINE LIFF および Dashboard からの POST リクエストを受容する。

#### 3. 動的地区ルーティングと認証・認可の完全分離
- **`districtId` は「Routing Hint」**: クライアントから送信される `districtId` は「どのDBを候補として調べるか」の指定に過ぎず、利用者の身元や権限を証明するものではない。
- **処理パイプラインの厳格な順序**:
  ```text
  Request 受信
      ↓
  districtId 取得 (Routing Hint)
      ↓
  DISTRICT_REGISTRY による対象DB（Spreadsheet ID）候補の解決
      ↓
  LINE Access Token 検証 ➔ 認証済み lineUserId の取得 (Identity Proof)
      ↓
  対象DB（名簿シート）との突合 ➔ 地区所属・利用資格確認 (Authorization)
      ↓
  認可 PASS / DENY
      ↓
  Spreadsheet 業務操作
  ```
- **越境アクセス拒否**: 認証済み `lineUserId` が対象地区DBの名簿に存在しない場合、即座に `NOT_REGISTERED`（または `FORBIDDEN`）でアクセスを拒否する。

#### 4. 二段階SSOT体系（二重管理の排除）
- **`DISTRICT_REGISTRY` (Script Properties)**:
  - 責務: **「地区DB接続情報（どのSpreadsheetか）」の唯一のSSOT**。
  - 形式: JSON形式のキー・バリュー（`{ "KUWANA": "ss_id_1", "OKAYAMA-01": "ss_id_2" }`）。
- **`SYSTEM_INFO` (各地区スプレッドシート第1シート)**:
  - 責務: **「接続後の地区DB自身が持つ地区情報・契約状態等（そのSpreadsheetは何地区で、利用可能か）」のSSOT**。
- **二段階検証**: 親GASは `DISTRICT_REGISTRY` でDBを特定してオープンした後、必ず当該DB内の `SYSTEM_INFO` を検証し、地区名の取り違えや契約終了状態がないことを二重検証（Integrity Guard）する。

## 3. Consequences (影響と効果)

### ポジティブな影響
- **量産作業の劇的短縮**: 新地区追加時に GAS 作成、clasp push、OAuth 画面での人的承認作業が一切発生しない。
- **エンドポイントの一元化**: 全地区で API URL が同一となり、フロントエンドの接続先管理が極めてシンプルになる。
- **安全な即時ロールバック**: 同一 Deployment ID のバージョン切り替えにより、クライアント設定に触れることなく数秒で前バージョンへ復旧できる。
- **認可境界の厳格化**: クライアント送信の `districtId` を盲信せず、LINE 認証と名簿照合を必須とすることで、地区越境アクセスが論理的に排除される。

### ネガティブな影響・トレードオフ
- **Script Properties の容量管理**: `DISTRICT_REGISTRY` は Script Properties（9KB/プロパティ上限）に格納するため、数百地区を超える超大規模運用時はレジストリ分割やマスターDB化の検討が必要となる（初期数十地区では全く問題なし）。
- **親GASの権限一括性**: 親GASの実行アカウント（デプロイ者）が全地区スプレッドシートに対するアクセス権限（編集権限）を保持している必要がある。

## 4. Verification (検証要件)

1. **認可境界テスト (Cross-District Authorization Test)**:
   - `User A (District A所属)` が `District A` を指定 ➔ **PASS**
   - `User A (District A所属)` が `District B` を指定 ➔ **DENY** (`NOT_REGISTERED`)
   - `Unknown User` が `District A` を指定 ➔ **DENY** (`NOT_REGISTERED`)
   - `Invalid / Expired Token` を指定 ➔ **DENY** (`UNAUTHORIZED`)
   - 存在しない `Unknown districtId` を指定 ➔ **DENY** (`DISTRICT_NOT_FOUND`)
2. **動的ルーティングテスト (Dynamic Routing Test)**:
   - 同一 Web App URL に対して異なる `districtId` を送信し、それぞれの独立したスプレッドシートへ正しく読み書きが行われることの検証。
3. **バージョン更新・ロールバック実機検証 (Version Redeploy & Rollback Test)**:
   - 既存 Deployment ID に対して Version をインクリメント更新し、URL 不変で反映されること、および旧 Version への即時切り戻しが成立することの実証。
